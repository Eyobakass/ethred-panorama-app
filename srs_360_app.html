1 Introduction & Executive Summary

1.1 Purpose of This Document

This Software Requirements Specification (SRS) defines the complete, authoritative, and developer-ready requirements for the Android 360° Panorama Capture & Virtual Tour Application. It is intended to be used directly by Android developers, QA engineers, and frontend integration engineers building the Pannellum.js-based viewer without any ambiguity.

This document covers all functional requirements, non-functional constraints, data schema integration contracts, use case scenarios, security requirements, testing strategy, and a ready-to-use prompt for AI-assisted development. Every requirement is explicitly aligned with the existing Ethred Backend API to guarantee zero breaking changes.

1.2 Project Overview

The Ethred platform is a real estate marketplace operating in Ethiopia. Property agents and sellers currently upload flat 2D images and videos of properties. The objective of this project is to allow agents to capture professional-quality 360° equirectangular panoramas of property rooms using nothing more than an ordinary Android smartphone with a hardware gyroscope, and to publish those panoramas as interactive virtual tours viewable on the Ethred web platform — exactly like those seen on Redfin or Matterport.

The original SRS concept conflicted with the existing backend in the following ways. This section documents what changed and why:

2.3 On-Device Stitching Pipeline (Step-by-Step)

  1. Frame Input: 24–36 raw JPEG frames (3264×2448 px each) passed to native C++ via JNI as byte arrays.
  2. Decode & Resize: OpenCV decodes each frame into a cv::Mat and downsamples to 1920×1440 px for feature detection (full resolution used for final blend).
  3. AKAZE Feature Detection: Per-frame keypoints and binary descriptors extracted using cv::AKAZE::create().
  4. Feature Matching & Filtering: FLANN-based matcher with ratio test (Lowe's ratio 0.75) identifies valid correspondences. Homography validated via RANSAC.
  5. Gyro-Assisted Camera Rotation Estimation: Initial rotation estimates seeded from logged Rotation Vector sensor data, refined by homography decomposition for accuracy.
  6. Spherical Warping: Each frame warped onto a sphere using cv::detail::SphericalWarper with focal length estimated from EXIF FOV data or manual calibration lookup table per device model.
  7. Seam Finding: Optimal seams between overlapping warp regions computed with cv::detail::GraphCutSeamFinder for the most visually seamless transitions.
  8. Exposure Compensation: cv::detail::BlocksGainCompensator equalizes brightness/color temperature across all frames before blending.
  9. Multi-Band Blending: cv::detail::MultiBandBlender with 5 pyramid levels blends seam regions to eliminate ghost artifacts.
  10. Equirectangular Crop & Scale: Output cropped to 2:1 aspect ratio (target 8192×4096 px for high-end, 4096×2048 for standard). Missing pole regions filled with mask for inpainting pass.
  11. Inpainting Pass: cv::inpaint() with Navier-Stokes algorithm fills zenith and nadir regions. Nadir optionally receives agency logo cap overlay.
  12. EXIF XMP Write: GPano metadata tags written to output JPEG: ProjectionType=equirectangular, UsePanoramaViewer=true, FullPanoWidthPixels, FullPanoHeightPixels.
  13. Output: Final equirectangular JPEG saved to local Room360/sessions/{session_id}/ directory.

3.2 Android Local Room Database Schema

The Android app maintains its own local SQLite database (via Room) for managing capture sessions offline and queuing uploads:

-- Table: capture_sessions
CREATE TABLE capture_sessions (
  id              TEXT PRIMARY KEY,   -- UUID v4
  property_id     TEXT NOT NULL,      -- Foreign key to ethred property
  room_name       TEXT NOT NULL,      -- e.g. "Living Room"
  status          TEXT NOT NULL,      -- CAPTURING | STITCHING | DONE | UPLOADING | UPLOADED | FAILED
  frame_count     INTEGER DEFAULT 0,
  output_path     TEXT,               -- Local file path of finished panorama JPEG
  created_at      INTEGER,            -- Unix epoch ms
  uploaded_at     INTEGER             -- Null until uploaded
);

-- Table: captured_frames
CREATE TABLE captured_frames (
  id              TEXT PRIMARY KEY,
  session_id      TEXT NOT NULL,
  file_path       TEXT NOT NULL,      -- Local path to raw JPEG frame
  yaw_deg         REAL NOT NULL,      -- Gyro yaw at moment of capture
  pitch_deg       REAL NOT NULL,
  roll_deg        REAL NOT NULL,
  captured_at     INTEGER
);

-- Table: hotspots
CREATE TABLE hotspots (
  id              TEXT PRIMARY KEY,
  from_session_id TEXT NOT NULL,      -- Scene A
  to_session_id   TEXT NOT NULL,      -- Scene B (target)
  pitch           REAL NOT NULL,      -- Pannellum pitch coordinate
  yaw             REAL NOT NULL,      -- Pannellum yaw coordinate
  label           TEXT                -- e.g. "Go to Kitchen"
);

-- Table: upload_queue
CREATE TABLE upload_queue (
  id              TEXT PRIMARY KEY,
  session_id      TEXT NOT NULL,
  property_id     TEXT NOT NULL,
  file_url        TEXT,               -- Populated after successful upload
  media_category  TEXT NOT NULL,      -- "IMAGE" or "DOCUMENT"
  sort_order      INTEGER DEFAULT 0,
  retry_count     INTEGER DEFAULT 0,
  status          TEXT DEFAULT 'PENDING' -- PENDING | IN_PROGRESS | DONE | FAILED
);

4 Functional Requirements

4.1 Authentication & Authorization (FR-AUTH)

FR-AUTH-01
JWT Login via Existing Auth API
The application MUST authenticate users by sending credentials to POST /api/v1/auth/login and securely storing the returned JWT access token in Android EncryptedSharedPreferences (AES-256 encrypted).
  • Token MUST be attached as Authorization: Bearer {token} header on every API request
  • App MUST detect token expiry (HTTP 401 response) and trigger re-authentication flow without data loss
  • Token MUST be cleared on explicit user logout
FR-AUTH-02
Role-Based Access Control
Only users with roles AGENT or SELLER (as returned in the JWT payload or user profile API) MUST be permitted to access the 360° capture feature. Buyers should see a read-only message directing them to the web viewer.

4.2 Gyroscope-Guided Frame Capture (FR-CAP)

FR-CAP-01
Hardware Sensor Initialization & Validation
On capture screen launch, the app MUST verify the presence of a hardware gyroscope using PackageManager.FEATURE_SENSOR_GYROSCOPE. If absent, a clear error dialog MUST be shown with the message: "This device does not have a gyroscope sensor, which is required for 360° capture. Please use a compatible Android device."
  • Use SensorManager.TYPE_ROTATION_VECTOR for fused orientation (gyro + accelerometer + magnetometer)
  • Sensor update interval: SensorManager.SENSOR_DELAY_UI (approx. 16ms)
  • Apply low-pass filter to raw sensor data to smooth jitter: filteredAngle = α × previous + (1 - α) × raw where α = 0.15
FR-CAP-02
Spherical Target Grid (Capture Reticle Overlay)
The capture UI MUST display a live augmented-reality style reticle overlaid on the CameraX viewfinder. The reticle maps the phone's current orientation to a 2D projection of the capture sphere, visually guiding the user to systematically cover all angles.
Capture Grid Structure:
  • Upper Ring (Pitch +30°): 8 evenly spaced target dots at yaw intervals of 0°, 45°, 90°, 135°, 180°, 225°, 270°, 315°
  • Horizontal Ring (Pitch 0°): 12 target dots at yaw intervals of 30°
  • Lower Ring (Pitch -30°): 8 evenly spaced target dots
  • Total: 28 target dots (minimum; user may capture more)
Dot State Colors:
  • ⚪ Gray: Not yet captured
  • 🔵 Blue pulsing: Currently in alignment zone (within ±3°)
  • 🟢 Green checkmark: Successfully captured
FR-CAP-03
Auto-Trigger Frame Capture
The camera MUST automatically capture a frame using CameraX ImageCapture.takePicture() when the following conditions are met simultaneously:
  • Phone orientation is within ±2° tolerance of a target dot
  • Orientation has been stable within this zone for ≥ 300ms (debounce period)
  • Camera auto-focus and auto-exposure have converged (AE state = CONVERGED)
  • The target dot has NOT already been captured (prevents duplicate frames)
On capture trigger:
  • Screen MUST flash white briefly (shutter animation)
  • Device MUST produce haptic feedback (short single vibration)
  • The captured dot MUST immediately turn green with a checkmark animation
  • A progress indicator shows X/28 frames captured
FR-CAP-04
Capture Quality Settings
The CameraX ImageCapture configuration MUST use the following settings for optimal stitching quality:
  • Resolution: ResolutionStrategy.HIGHEST_AVAILABLE_STRATEGY (or minimum 12MP / 4032×3024)
  • JPEG Quality: 95% (not 100% to avoid excessively large files)
  • White Balance: AWB_MODE_AUTO — locked after first frame capture to ensure color consistency across all frames
  • Exposure: AE locked after first frame capture
  • Flash: Disabled (flash causes uneven exposure across panorama)
  • Zoom: Fixed at 1.0× (no optical zoom)
FR-CAP-05
Manual Override & Completion
The user MUST be able to manually tap any target dot to force capture at that position. The user MUST also be able to complete capture early once a minimum of 16 frames have been captured (covering approximately 80% of the horizontal rings) via a "Finish Capture" button.
FR-CAP-06
Session Recovery
If the app is backgrounded or the device is rotated during capture, the session MUST resume from where it left off. Already-captured dots MUST remain green and the remaining frames must still be capturable. Captured frames MUST be persisted to the Room database immediately after capture.

4.3 On-Device OpenCV Stitching Engine (FR-STITCH)

FR-STITCH-01
Native C++ OpenCV NDK Integration
The stitching engine MUST be implemented in C++ using OpenCV 4.8+ compiled for Android ARM64 (ABI: arm64-v8a and armeabi-v7a for compatibility). The native library MUST be exposed to Kotlin via a JNI bridge class.
  • Native library file: libstitcher.so
  • JNI class: com.ethred.panorama.stitching.NativeStitcher
  • Method: external fun stitchFrames(framePaths: Array<String>, gyroDegrees: FloatArray, outputPath: String): StitchResult
FR-STITCH-02
AKAZE Feature Detection & Matching
The stitching pipeline MUST use AKAZE (Accelerated-KAZE) feature detection as the primary algorithm. ORB MUST be available as a fallback for devices with insufficient RAM (<3GB) since AKAZE is more memory intensive.
Parameters for AKAZE:
  • descriptor_type = DESCRIPTOR_MLDB
  • descriptor_size = 0 (full size)
  • threshold = 0.001f
  • Matching: cv::FlannBasedMatcher with LSH index (binary descriptors)
  • Ratio test threshold: 0.75 (Lowe's ratio)
  • RANSAC threshold: 4.0 pixels for homography rejection
FR-STITCH-03
Spherical Projection, Seam Carving & Multi-Band Blending
The stitching pipeline MUST execute the full OpenCV detail stitching pipeline:
  • Warper: cv::detail::SphericalWarper with focal length estimated from camera EXIF metadata (focal_length_mm / sensor_width_mm × image_width_px). Fallback: device model lookup table (provided in code as a hardcoded map of common devices).
  • Exposure Compensation: cv::detail::BlocksGainCompensator with block_size=32
  • Seam Finder: cv::detail::GraphCutSeamFinder(COST_COLOR_GRAD)
  • Blender: cv::detail::MultiBandBlender with num_bands=5
  • Output: cv::Mat converted to cv::IMWRITE_JPEG_QUALITY=92
FR-STITCH-04
Output Resolution & EXIF Metadata
The stitching pipeline MUST produce an equirectangular JPEG at 2:1 aspect ratio:
Resolution tiers based on device RAM:
  • >6GB RAM: 8192×4096 px (high resolution)
  • 3–6GB RAM: 4096×2048 px (standard resolution)
  • <3GB RAM: 2048×1024 px (compact resolution)
Required EXIF XMP metadata (GPano namespace):
  • GPano:ProjectionType = equirectangular
  • GPano:UsePanoramaViewer = True
  • GPano:FullPanoWidthPixels = [output_width]
  • GPano:FullPanoHeightPixels = [output_height]
  • GPano:CroppedAreaImageWidthPixels = [output_width]
  • GPano:CroppedAreaImageHeightPixels = [output_height]
  • GPano:CroppedAreaLeftPixels = 0
  • GPano:CroppedAreaTopPixels = 0

4.4 Gap Inpainting & Post-Processing (FR-FILL)

FR-FILL-01
Zenith (Ceiling/Sky) Inpainting
The top circular region of the equirectangular output (the zenith, approximately 10–15% of image height) will be missing due to hardware limitations of handheld capture. The engine MUST apply cv::inpaint(src, mask, dst, inpaintRadius=3, INPAINT_NS) where the mask covers this missing region, propagating surrounding texture upward seamlessly.
FR-FILL-02
Nadir (Floor/Feet) Coverage
The nadir (bottom circular region) will contain the user's feet and floor. The app MUST offer the user three nadir cap options before uploading:
  • Auto Inpaint: Run cv::inpaint to fill the area with a continuation of the floor texture
  • Smooth Blur Gradient: Apply a circular radial gradient feathering the bottom to neutral gray/black
  • Agency Logo Cap: Overlay a pre-set circular agency/brand logo image (loaded from app settings) centered at the nadir point — this is the professional standard used by Matterport
FR-FILL-03
Automatic Horizon Leveling
The stitching engine MUST auto-correct horizon tilt by analyzing the gravitational vector logged during capture sessions and applying a roll correction rotation to the final equirectangular output, ensuring the horizon appears straight when viewed in a browser.

4.5 Multi-Room Tour Builder (FR-TOUR)

FR-TOUR-01
Property Session Management
The app MUST allow users to create a capture session linked to a specific property (identified by its backend property_id). Within each property session, users MUST be able to add, name, and re-order multiple individual room captures (up to 20 rooms per property).
FR-TOUR-02
Interactive Hotspot Placement Editor
After stitching, the app MUST display an interactive 360° preview of each room (using an in-app WebView with Pannellum.js or SceneView). The user MUST be able to long-press anywhere on the 360° preview to drop a hotspot marker. A bottom sheet dialog MUST appear prompting them to select the target room this hotspot links to.
  • Dropped hotspot position MUST record the Pannellum-compatible pitch and yaw coordinates (in degrees)
  • Hotspots MUST be visually represented by an animated arrow icon in the preview
  • Maximum 5 hotspots per room scene
  • Hotspots MUST be editable (tap to change target) and deletable (long-press to remove)
FR-TOUR-03
Tour Manifest Generation
When the user finalizes a multi-room tour, the app MUST generate a valid tour_manifest.json file (as defined in Section 3.3) and save it locally. This manifest MUST be uploaded to the backend as a separate file and registered as a DOCUMENT type media asset with sort_order: 0.

4.6 Backend Upload & Sync (FR-SYNC)

FR-SYNC-01
Network-Resilient Upload Queue
All uploads (panorama JPEGs and manifest JSON) MUST be enqueued in the Room upload_queue table immediately. A WorkManager UploadWorker MUST process this queue with the following constraints:
  • Constraint: NetworkType.CONNECTED (executes only when online)
  • Retry policy: Exponential backoff starting at 30 seconds, max 5 retries
  • If all retries fail, the queue item MUST be marked FAILED and the user MUST be shown an inline notification with a "Retry" action
  • Upload progress MUST be shown in the Android notification drawer as a persistent notification with a progress bar
FR-SYNC-02
Thumbnail Generation
Before upload, the app MUST generate a 512×256 px thumbnail JPEG of the equirectangular panorama for display in the property listing's media gallery. The thumbnail MUST be uploaded alongside the full-resolution panorama and registered as a separate IMAGE media entry.
FR-SYNC-03
Post-Upload Cleanup
After all files for a property session have been successfully uploaded and confirmed by the backend (HTTP 200/201), the app MUST:
  • Mark all queue items as DONE in the Room DB
  • Delete raw captured frames from local storage (to free device storage)
  • Retain only the final stitched JPEG locally (for offline preview)
  • Display a success confirmation dialog with a "View on Website" deeplink option

4.7 Local Preview Viewer (FR-VIEW)

FR-VIEW-01
In-App 360° Preview Before Upload
After stitching completes, the app MUST immediately display a fully interactive 360° panorama preview using a WebView-embedded Pannellum.js viewer (or SceneView) loaded from a local file:// path — no internet connection required. The user MUST be able to pan, tilt, and zoom within the preview before deciding to approve or retake the panorama.
FR-VIEW-02
Capture Quality Scoring
The app MUST display an automatic quality score on the preview screen (1–5 stars) derived from the stitching engine's internal metrics:
  • Number of matched feature keypoints (higher = better)
  • Reprojection error from RANSAC homography (lower = better)
  • Percentage of inpainted regions (lower = better)
  • A low quality score (≤ 2 stars) MUST trigger a prominent warning recommending retake

5.2 Memory & Storage Management (NFR-MEM)

  • Every cv::Mat object allocated in the native C++ layer MUST be explicitly released via mat.release() or destructor pattern to prevent native heap OOM crashes.
  • Input frames MUST be processed one-at-a-time in the feature detection phase, not all loaded simultaneously into memory.
  • App MUST check available storage before starting a capture session. Minimum required: 500MB free (for 36 raw frames at ~5MB each + output panorama + temp files). If insufficient, the user MUST be warned with an option to free storage before proceeding.
  • Raw frames MUST be deleted from local storage immediately after successful upload to the backend.
  • Stitched panoramas MUST be kept locally for 30 days then automatically removed if they have been successfully uploaded (configurable in settings).

9 Security Requirements

SEC-01
Secure Token Storage
The JWT access token MUST be stored in EncryptedSharedPreferences using MasterKey.Builder with AES-256-GCM encryption backed by Android Keystore. The token MUST NEVER be stored in plain SharedPreferences, plain text files, or the Room database.
SEC-02
Certificate Pinning
All HTTPS network calls to the Ethred backend MUST use OkHttp's CertificatePinner with the backend server's SSL certificate SHA-256 hash pinned. This prevents man-in-the-middle (MITM) attacks on the uploaded photo data.
SEC-03
No Cloud Key Management for Free Services
As all processing is on-device and free, no API keys, external AI/cloud service keys, or third-party service credentials are stored or transmitted. The only credentials handled are user JWT tokens from the existing Ethred auth service.
SEC-04
Local File Privacy
Captured frames and stitched panoramas MUST be stored in the app's internal storage directory (context.filesDir), which is not accessible to other apps or the Android media gallery without explicit user share action. The android:sharedUserId attribute MUST NOT be used.
SEC-05
ProGuard / R8 Obfuscation
Release builds MUST enable R8 code shrinking and obfuscation to protect business logic. Native C++ code is inherently binary-only. ProGuard rules MUST be configured to preserve Room DB, Retrofit interfaces, and Hilt DI entry points.

═══════════════════════════════════════════════════
STITCHING PIPELINE (Native C++ / OpenCV NDK)
═══════════════════════════════════════════════════
JNI Bridge class: com.ethred.panorama.stitching.NativeStitcher
Native library: libstitcher.so (arm64-v8a + armeabi-v7a)

Pipeline steps:
1. Decode frames to cv::Mat, downsample to 1920x1440 for feature detection
2. AKAZE feature detection (fallback: ORB for <3GB RAM devices)
3. FLANN-based matching with Lowe's ratio test 0.75
4. RANSAC homography estimation (threshold: 4.0 px)
5. cv::detail::SphericalWarper (focal length from EXIF or device table)
6. cv::detail::BlocksGainCompensator (block_size=32)
7. cv::detail::GraphCutSeamFinder (COST_COLOR_GRAD)
8. cv::detail::MultiBandBlender (num_bands=5)
9. Output at 4096x2048 (mid-range) or 8192x4096 (high-end, >6GB RAM)
10. cv::inpaint zenith + nadir missing regions (INPAINT_NS method)
11. Optional: Nadir logo cap overlay from agency branding settings
12. Embed GPano XMP EXIF metadata into output JPEG
13. Generate 512x256 thumbnail for property gallery

Quality score (1-5 stars) based on:
- RANSAC inlier ratio (higher = better)
- % inpainted area (lower = better)
- Feature match count (higher = better)

If quality score ≤ 2: show prominent retake warning
